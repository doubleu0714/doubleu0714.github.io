[코루틴 글](/posts/kotlin-coroutines/)에서는 `suspend` 함수로 "기다리는 동안 스레드를 놓아주는" 방법을 봤습니다. 그런데 `suspend` 함수는 한 번 기다린 뒤 **값 하나**를 돌려주고 끝납니다. 현실의 데이터는 그렇지 않은 경우가 많습니다. 실시간 주문 현황, 검색창에 입력하는 글자, 센서가 계속 보내는 측정값처럼 **값이 시간에 걸쳐 여러 개** 도착합니다.

이 글에서는 그런 값의 흐름을 다루는 코루틴의 도구, **Flow**를 소개합니다. 코루틴 글에서 쓴 식당 비유를 그대로 이어서 설명하니, 먼저 읽고 오시면 더 편합니다.

## 왜 Flow를 쓸까?

**1. 왜 Flow를 쓰나요?**
**시간에 걸쳐 여러 개 도착하는 값**을, 코루틴처럼 순차 코드 모양으로 다루고 싶어서입니다.

**2. 왜 `suspend` 함수만으로는 부족한가요?**
`suspend` 함수는 값을 **하나만** 돌려주기 때문입니다. `List`로 여러 개를 돌려줄 수도 있지만, 그러면 모든 값이 준비될 때까지 기다린 뒤에 한꺼번에 받아야 합니다. 첫 번째 값이 일찍 준비돼도 마지막 값이 나올 때까지 쓸 수 없습니다.

**3. 그래서 이전에는 어떻게 했나요?**
콜백이나 리스너("값이 올 때마다 이 함수를 불러 줘")를 등록하거나, RxJava 같은 리액티브 라이브러리를 썼습니다. 값이 올 때마다 반응할 수 있다는 장점이 있었습니다.

**4. 그 방식의 한계는 무엇이었나요?**
콜백은 흐름이 여러 함수로 흩어져 읽기 어렵고, 예외 처리와 취소가 번거롭습니다. 리액티브 라이브러리는 강력하지만 **연산자의 종류가 매우 많아서 배우기 어렵고**, 코루틴 코드와 섞어 쓸 때 별도의 변환이 필요했습니다.

**5. Flow는 이 한계를 어떻게 극복했나요?**
Flow는 코루틴 위에서 동작하는 값의 흐름입니다. `suspend` 함수를 그대로 쓸 수 있고, `for` 문처럼 읽히는 `collect`로 값을 받으며, **취소와 예외 처리도 코루틴의 규칙을 그대로 따릅니다.** 새로 배울 개념이 적습니다.

> 🎯 **사용하는 이유:** 여러 번 도착하는 값을, 값이 준비되는 대로 순차 코드처럼 처리하기 위해서입니다.
>
> 🎯 **극복한 문제:** 값이 여러 개일 때 "한꺼번에 받는 `List`"는 느리고, "콜백이나 리액티브 라이브러리"는 읽기 어렵고 배우기 어려웠던 문제를, 코루틴의 순차 코드 모양 그대로 해결했습니다.

## 기본 개념

> 🍳 **비유: 주방의 배식구**
>
> 코스 요리를 주문했다고 해 봅시다. 방식은 두 가지입니다.
>
> 하나는 **모든 요리가 완성될 때까지 기다렸다가 한 쟁반에 담아 내오는 방식**입니다. 샐러드가 5분 만에 완성돼도 스테이크가 나올 때까지 손님은 아무것도 못 먹습니다. `List`가 이렇습니다.
>
> 다른 하나는 **요리가 완성되는 대로 배식구로 하나씩 내보내는 방식**입니다. 손님은 샐러드를 먼저 먹기 시작합니다. 이것이 Flow입니다.

| 용어 | 식당 비유 | 설명 |
| --- | --- | --- |
| `Flow` | 배식구 | 값이 하나씩 흘러나오는 통로 |
| `flow { }` 빌더 | 주방의 조리 과정 | 값을 만들어 내보내는 코드 |
| `emit` | 배식구에 요리를 올려놓기 | 값 하나를 내보냅니다 |
| `collect` | 홀에서 요리를 받아 서빙하기 | 흘러나오는 값을 하나씩 받습니다 |
| 연산자 (`map`, `filter` 등) | 배식구와 테이블 사이의 손질 | 흐르는 값을 변환하거나 걸러냅니다 |

### 콜드 스트림: 받는 사람이 있어야 만들기 시작합니다

Flow의 가장 중요한 성질은 **`collect`를 호출하기 전까지는 아무 일도 일어나지 않는다**는 점입니다. 이를 **콜드(Cold) 스트림**이라고 합니다.

> 🍳 **비유: 주문이 들어와야 조리를 시작하는 주방**
>
> 미리 만들어 둔 음식을 진열하는 뷔페가 아니라, **주문서가 들어와야 비로소 불을 켜는** 식당입니다. 같은 주문을 두 번 넣으면 주방은 처음부터 두 번 조리합니다.

### 동작 순서

1. `flow { }`로 조리 과정을 정의합니다. 이 시점에는 아무것도 실행되지 않습니다.
2. 누군가 `collect`를 호출하면 그제서야 블록이 실행됩니다.
3. 블록 안에서 `emit`으로 값을 내보낼 때마다, `collect`의 블록이 그 값을 받아 처리합니다.
4. 마지막 값까지 모두 내보내면 `collect`가 끝납니다.

## 다른 방식과 비교

| 방식 | 비유 | 장점 | 한계 |
| --- | --- | --- | --- |
| `List` | 전부 완성된 뒤 한 쟁반에 | 단순함 | 모두 준비될 때까지 기다려야 하고 메모리를 많이 씁니다 |
| `Sequence` | 홀 직원이 주방에 직접 가서 하나씩 가져오기 | 값을 하나씩 처리합니다 | 중간에 기다리는 `suspend` 호출을 쓸 수 없고 스레드를 막습니다 |
| 콜백 | "요리가 되면 이 벨을 울려 주세요" | 되는 대로 반응합니다 | 흐름이 흩어져 읽기 어렵습니다 |
| `Flow` | 배식구 | 되는 대로 받고, 기다리는 동안 스레드를 놓아줍니다 | 코루틴 개념을 알아야 합니다 |

## 사용 예제

이제부터는 개발자를 위한 실전 코드입니다. Kotlin 2.4, kotlinx-coroutines 1.11.0, JDK 21 기준입니다. Flow는 `kotlinx-coroutines-core`에 포함되어 있어서 [코루틴 글](/posts/kotlin-coroutines/)의 준비물 그대로 쓰면 됩니다.

### 가장 기본: `flow`와 `collect`

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun cookings(): Flow<String> = flow {
    println("[주방] 조리 시작")
    for (menu in listOf("샐러드", "파스타", "스테이크")) {
        delay(300)   // 조리하는 동안 스레드를 놓아줌
        emit(menu)
    }
}

fun main() = runBlocking {
    val f = cookings()
    println("flow 만듦 (아직 조리 안 함)")
    f.collect { println("서빙: $it") }
    f.collect { println("한 번 더: $it") }
}
```

실행 결과입니다.

```text
flow 만듦 (아직 조리 안 함)
[주방] 조리 시작
서빙: 샐러드
서빙: 파스타
서빙: 스테이크
[주방] 조리 시작
한 번 더: 샐러드
한 번 더: 파스타
한 번 더: 스테이크
```

`cookings()`를 호출한 시점에는 `[주방] 조리 시작`이 찍히지 않고, `collect`를 호출하자 그제서야 찍힙니다. 같은 Flow를 두 번 `collect`하면 조리도 **처음부터 두 번** 실행됩니다. 콜드 스트림의 성질입니다.

### 연산자로 손질하기

컬렉션에서 쓰던 `map`, `filter`를 Flow에서도 똑같이 쓸 수 있습니다.

```kotlin
(1..5).asFlow()
    .filter { it % 2 == 1 }
    .map { "메뉴 $it" }
    .collect { println(it) }   // 메뉴 1, 메뉴 3, 메뉴 5
```

| 연산자 | 하는 일 | 비유 |
| --- | --- | --- |
| `map` | 값을 다른 값으로 바꿉니다 | 접시에 담기 전에 플레이팅하기 |
| `filter` | 조건에 맞는 값만 통과시킵니다 | 상태가 나쁜 요리는 돌려보내기 |
| `onEach` | 값을 건드리지 않고 중간에 확인합니다 | 지나가는 요리 사진 찍기 |
| `take` | 앞의 몇 개만 받고 끝냅니다 | 한 테이블에 두 접시까지만 내기 |
| `first`, `toList` | 값 하나, 또는 전체를 받고 끝냅니다 | 첫 접시만 받기, 전부 모아서 받기 |

`map`이나 `filter` 안에서도 `suspend` 함수를 호출할 수 있다는 점이 `Sequence`와 다릅니다.

### 소비자가 느릴 때: `buffer`

생산자가 100ms마다 값을 내보내는데, 받는 쪽이 값 하나를 처리하는 데 300ms가 걸린다고 해 봅시다. 기본적으로 Flow는 **한 값이 완전히 처리된 뒤에야 다음 값을 만듭니다.**

```kotlin
val slow = flow { repeat(3) { delay(100); emit(it) } }

slow.collect { delay(300) }            // 약 1214ms
slow.buffer().collect { delay(300) }   // 약 1037ms
```

`buffer()`는 생산자와 소비자를 **서로 다른 코루틴**으로 분리하고 그 사이에 임시 보관함을 둡니다. 소비자가 서빙하는 동안 주방은 다음 요리를 미리 만들 수 있습니다. 이 예제는 숫자 3개뿐이라 차이가 작지만 개수가 많아질수록 벌어집니다. 시간은 실행 환경에 따라 달라질 수 있습니다.

> 🍳 **비유: 배식구 옆 선반**
>
> 서빙 직원이 느리면 요리가 배식구에 쌓여 주방도 손을 놓게 됩니다. `buffer`는 배식구 옆에 선반을 두어서, 주방은 선반에 계속 올려놓고 서빙 직원은 자기 속도대로 가져가게 하는 것입니다.

### 어느 스레드에서 실행할지: `flowOn`

```kotlin
flow { emit(readFile()) }   // 블로킹 입출력이라고 가정
    .flowOn(Dispatchers.IO)  // 위쪽(생산)만 IO 디스패처에서 실행
    .collect { println(it) } // collect는 호출한 쪽의 코루틴에서 실행
```

`flowOn`은 **자기보다 위쪽에 있는 코드**의 실행 위치만 바꿉니다. 이렇게 하면 주방(생산)은 IO 담당 요리사가, 서빙(소비)은 원래 요리사가 맡게 됩니다. 앞의 `withContext` 대신 Flow 안에서는 이 방법을 써야 하는 이유는 아래 주의할 점에서 설명합니다. 실행 위치를 정하는 Dispatcher 자체가 궁금하다면 [코루틴 Dispatcher 글](/posts/kotlin-dispatchers/)을 참고하세요.

### 예외 처리: `catch`

```kotlin
flow {
    emit(1)
    throw IllegalStateException("재료 소진")
}
    .catch { println("catch: ${it.message}"); emit(-1) }
    .collect { println(it) }
// 1
// catch: 재료 소진
// -1
```

`catch`는 **자기보다 위쪽**에서 발생한 예외만 잡습니다. 아래쪽 `collect` 블록에서 난 예외는 잡지 못하므로 그 부분은 `try-catch`로 감싸야 합니다.

### 상태를 들고 있는 Flow: `StateFlow`

지금까지의 Flow는 `collect`할 때마다 새로 시작하는 콜드 스트림이었습니다. 반대로 **항상 켜져 있고 현재 값을 하나 들고 있는** 핫(Hot) 스트림도 있습니다. 그중 `StateFlow`는 "현재 상태"를 표현합니다.

> 🍳 **비유: 주문 현황 전광판**
>
> 전광판에는 항상 **지금의 상태**가 하나 떠 있습니다. 새로 온 손님이 전광판을 봐도 "접수" 또는 "조리중" 같은 최신 상태를 바로 알 수 있습니다. 과거에 어떤 순서로 바뀌었는지는 기억하지 않습니다.

```kotlin
val state = MutableStateFlow("접수")
val job = launch { state.collect { println("현황: $it") } }

delay(50); state.value = "조리중"
delay(50); state.value = "조리중"   // 같은 값이라 알림이 가지 않음
delay(50); state.value = "완료"
delay(50)
job.cancel()
// 현황: 접수
// 현황: 조리중
// 현황: 완료
```

- 처음부터 값이 있어야 합니다 (초기값 필수).
- **값이 같으면 다시 알리지 않습니다.** 위 예제에서 `조리중`을 두 번 넣었지만 한 번만 출력됩니다.
- 구독자가 늦게 와도 가장 최근 값을 바로 받습니다.

Android의 화면 상태나 서버 내부의 설정값처럼 "현재 값"이 중요한 곳에 알맞습니다.

### 이벤트를 알리는 Flow: `SharedFlow`

`SharedFlow`는 "상태"가 아니라 **일어난 일**(이벤트)을 여러 구독자에게 동시에 알릴 때 씁니다.

> 🍳 **비유: 호출벨 방송**
>
> "7번 손님, 음식 나왔습니다" 방송은 그 순간 홀에 있는 모두에게 들립니다. 방송이 끝난 뒤 들어온 손님은 이미 지나간 방송을 들을 수 없습니다.

```kotlin
val shared = MutableSharedFlow<String>()
val a = launch { shared.collect { println("A: $it") } }
val b = launch { shared.collect { println("B: $it") } }

delay(50)
shared.emit("호출벨 울림")   // A와 B 모두 받음
delay(50)
a.cancel(); b.cancel()
// A: 호출벨 울림
// B: 호출벨 울림
```

| 종류 | 성질 | 비유 | 어울리는 곳 |
| --- | --- | --- | --- |
| `Flow` (`flow { }`) | 콜드. `collect`마다 새로 시작 | 주문마다 새로 하는 조리 | 요청 한 번에 결과가 여러 개 나오는 작업 |
| `StateFlow` | 핫. 항상 최신 값 하나를 보관, 같은 값은 무시 | 주문 현황 전광판 | 화면 상태, 현재 설정값 |
| `SharedFlow` | 핫. 값을 보관하지 않고 구독자들에게 방송 (`replay`로 최근 값 재전송 가능) | 호출벨 방송 | 일회성 이벤트, 알림 |

## 사용 시 주의할 점

### 1. 콜드라는 사실을 잊지 마세요

같은 Flow를 여러 곳에서 `collect`하면 **그때마다 생산 코드가 처음부터 다시 실행됩니다.** 그 안에서 DB를 조회하거나 API를 호출한다면 호출이 여러 번 나갑니다. 한 번만 실행하고 결과를 여러 곳에 나눠 주고 싶다면 `shareIn`, `stateIn`으로 핫 스트림으로 바꾸세요.

### 2. `flow { }` 안에서 `withContext`로 `emit`하지 마세요

```kotlin
flow { withContext(Dispatchers.IO) { emit(1) } }.collect()
// IllegalStateException: Flow invariant is violated: ...
```

직접 실행하면 `Flow invariant is violated`라는 예외가 납니다. Flow는 값을 내보내는 코루틴과 받는 코루틴이 **같은 컨텍스트**에 있다는 약속을 지켜야 하기 때문입니다. 실행 위치를 바꾸려면 앞에서 본 `flowOn`을 쓰세요.

### 3. `collect`는 Flow가 끝날 때까지 돌아오지 않습니다

`StateFlow`나 `SharedFlow`는 **끝나지 않는 Flow**입니다. 그래서 `collect` 아래에 적은 코드는 영원히 실행되지 않습니다.

```kotlin
val k = launch {
    inf.collect { }
    println("여기는 도달 안 함")
}
```

여러 Flow를 동시에 수집하려면 각각 `launch { }` 안에서 `collect`하세요. 또 수집하는 코루틴이 취소되면 `collect`도 함께 끝나므로, 반드시 수명이 정해진 스코프 안에서 수집해야 합니다.

### 4. 값을 놓칠 수 있습니다 (StateFlow)

`StateFlow`는 소비자가 느리면 **중간 값을 건너뛰고 최신 값만** 전달합니다. 예컨대 "접수 → 조리중 → 완료"가 순식간에 바뀌면 소비자는 "완료"만 볼 수도 있습니다. 모든 변화를 하나도 빠짐없이 받아야 하는 용도라면 `SharedFlow`나 `Channel`이 맞습니다.

### 5. `catch`의 위치가 중요합니다

`catch`는 자신의 **위쪽**에서 발생한 예외만 잡습니다. `collect` 블록 안의 예외는 잡지 못합니다. 예외가 어디서 날 수 있는지를 기준으로 `catch`의 위치를 정하세요.

## 알아둘 점

> 💡 Flow는 단순한 데이터 변환에는 편하지만, 값의 흐름이 복잡해질수록 연산자 조합이 어려워질 수 있습니다. 먼저 `map`, `filter`, `collect`로 충분한지 확인하고, 필요할 때 `buffer`, `flowOn`, 핫 스트림을 하나씩 추가하세요.

- **연산자의 종류가 많습니다.** 이 글에서는 자주 쓰는 일부만 다뤘습니다. 값을 합치는 `combine`, `zip`, 새 값이 오면 이전 작업을 취소하는 `flatMapLatest` 등은 공식 문서에서 확인하세요.
- **이 글의 코드는 직접 실행해서 출력을 확인했습니다.** Kotlin 2.4.21, kotlinx-coroutines 1.11.0, JDK 21 환경이며, 시간 측정값은 실행 환경에 따라 달라질 수 있습니다.

## 정리

Flow는 **여러 개의 값을, 준비되는 대로 하나씩 받는** 코루틴의 도구입니다. 콜백 없이 순차 코드처럼 쓰면서 취소와 예외 처리도 코루틴 규칙을 그대로 따릅니다.

- **기본 개념:** `flow { }`로 만들고 `emit`으로 내보내며 `collect`로 받습니다. `collect` 전에는 아무것도 실행되지 않는 콜드 스트림입니다.
- **사용 예제:** `map`·`filter` 같은 연산자, `buffer`, `flowOn`, `catch`를 씁니다. 상태는 `StateFlow`, 이벤트는 `SharedFlow`로 다룹니다.
- **주의할 점:** 콜드라서 `collect`마다 다시 실행됩니다. `flow { }` 안에서 `withContext`로 `emit`하지 말고, `collect`는 끝나지 않을 수 있음을 기억하세요.

> 🎯 **사용하는 이유:** 여러 번 도착하는 값을, 값이 준비되는 대로 순차 코드처럼 처리하기 위해서입니다.
>
> 🎯 **극복한 문제:** "한꺼번에 받는 `List`는 느리고, 콜백과 리액티브 라이브러리는 읽기 어렵다"는 문제를, 코루틴의 순차 코드 모양 그대로 해결했습니다.

코루틴 자체가 낯설다면 [코루틴 글](/posts/kotlin-coroutines/)을 먼저 읽어 보세요. 더 나아가고 싶다면 코루틴 사이에 데이터를 주고받는 **`Channel`**, 여러 Flow를 합치는 `combine`, `flatMapLatest`를 살펴보세요.
